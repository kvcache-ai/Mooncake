## 0. 结论摘要

当前代码已经具备若干单机原型模块：页级 KV 管理、RadixTree 前缀缓存、FeatureStore、TransferPolicy、本地 TransferEngine、EPD worker、Workflow、调度与 offload 原型等。但整体仍停留在“单进程 / 本地 tensor copy / demo 验证”阶段，和 RFC 要求的“统一多模态状态对象 + EPD 三阶段分离 + 分布式 owner shard 控制面 + Agent 跨步骤复用 + A2A / Offload / 可靠性压测”存在显著缺口。

必须优先修复的 P0 问题：

1. **状态对象不符合 RFC v2 语义**：`MultimodalState` 缺少 `version_id`、`parent_version_id`、`snapshot_epoch`、`status`、`approximate`、全局 `BlockRef` 字段等，无法提供 workflow 内 snapshot isolation。
2. **引用计数只有本地 page manager 级别**：`BlockRef` 只有 `physical_id/filled`，没有 `global_block_id`、owner shard、逻辑位置、virtual offset；无法支持跨节点 fork、A2A、RDMA/TCP/SHM 统一 ownership。
3. **RadixTree scope 未实现**：`match_longest_prefix(scope=...)` 明确忽略 scope，可能跨 workflow 错复用 KV。
4. **FeatureStore 没有真实 refcount**：`incref` 只是刷新 LRU，`release` 是 no-op，不满足 RFC 的 FeatureBundle 生命周期要求。
5. **TransferEngine 跨节点路径未实现**：Mooncake 初始化后 `_remote_transfer` 仍 `NotImplementedError`，P→D/E→P/A2A/Offload 只有本地复制或 CPU round-trip 模拟。
6. **跨步骤复用缺少安全闸门**：当前 RelayRecompute 近似实现没有 Virtual-RoPE、KV Validity Check、attention drift estimator、fallback-safe 质量闸门。
7. **Offload 不是 RFC 的异步状态机**：当前 offload 同步复制 CPU、直接释放 GPU refs，无 `OFFLOADING/RESTORING` lock、ABORT_DMA、in-flight restore、MooncakeStore 语义。
8. **测试体系不合格**：`compileall` 通过；但 pytest 下 24 passed / 8 errors，Phase1/Phase3 的 real model 测试被 pytest 收集却缺 fixture，无法作为 CI gate。

本计划建议先完成语义地基与测试闸门，再推进真实 EPD / Mooncake / vLLM 集成，最后做 Agent 调度、A2A、RDMA 与评估矩阵。

## 1. 审查证据与现状问题

### 1.1 状态层问题

相关文件：

- `core/state/state.py`
- `core/state/page_manager.py`
- `core/state/radix_tree.py`
- `core/state/feature_store.py`
- `agent/coordination/workflow.py`

发现：

- `StateMeta` 只有 `token_ids/image_ids/agent_id/workflow_id/step/turn/ttl_deadline/priority`，缺少 RFC §4.1 的 `version_id/parent_version_id/snapshot_epoch/approximate/status`。
- `MultimodalState` 只有本地 `state_id/kv_refs/feature_hash/feature_hashes/meta`，没有不可变版本语义；fork 复制 meta 后直接登记 child，无法保证父状态并发 decode/fork 时的 snapshot isolation。
- `BlockRef` 只有 `physical_id` 和 `filled`，无法表达 RFC 要求的 `global_block_id/physical_node_id/logical_index/virtual_offset`。
- `PagedKVManager` 使用进程内 `_pages` 和 sharded lock，适合单机原型，但不具备 owner shard 权威、global GID、跨节点 CAS 提权、物理释放确认等能力。
- `StateLayer.handoff()` 只是改 `agent_id`，没有 2PC prepare/commit、目标节点 pull、失败回滚。
- `StateLayer.offload()` 直接 `release_refs` 并清空 `state.kv_refs`，对极速 restore、并发 fork、restore-after-fork race 没有锁语义。

### 1.2 前缀缓存 / 跨步骤复用问题

相关文件：

- `core/state/radix_tree.py`
- `core/state/relay_recompute.py`
- `agent/coordination/reuse_pipeline.py`
- `agent/coordination/workflow.py`

发现：

- `RadixTree.match_longest_prefix(..., scope=...)` 文档说明 scope 参数“accepted and ignored”，即 workflow 隔离没有实现。
- `RadixTree` 节点没有 workflow_id、epoch、version 或 owner metadata，无法实现 per-workflow snapshot 查询。
- `Workflow.advance()` 通过 `prev_tokens + new_tokens` 做 prefix 查询，但没有基于 `snapshot_epoch` 查询稳定版本。
- `RelayRecompute` 的 `residual_attention_merge()` 只是拼接 K/V，并没有真实 residual attention kernel、Virtual-RoPE、mask/position correctness 检查。
- `ReusePipeline` tier3 当前说明“Currently a no-op”，但测试描述把它当作完整 tier3 能力，存在能力声明与实现不一致。

### 1.3 FeatureBundle 缓存问题

相关文件：`core/state/feature_store.py`

发现：

- `hash_pixel_values()` 对大 tensor 采样哈希，RFC §6.9 要求 URL/path → 元数据 → 全量/异步三段式极速哈希，当前未实现 URL/path 和 metadata hash。
- `FeatureStore.incref()` 只是刷新 LRU；`release()` 是 no-op。RFC 要求 FeatureBundle 与 KV pages 一样具备引用计数与 owner shard 生命周期。
- FeatureBundle 无 owner、lease、ttl_deadline、refcount、状态锁，无法跨节点共享与 A2A 迁移。

### 1.4 传输层问题

相关文件：

- `core/transfer/policy.py`
- `core/transfer/engine.py`
- `core/transfer_engine.py`

发现：

- `TransferPolicy` 已有 mode/compress/precision/prefetch 枚举，但缺 RFC §5.5 的 cost model、adaptive controller、候选策略画像和 EWMA 回归。
- `TransferEngine.transfer_tensor()` 在 local 下执行 tensor copy；CacheGen 通过 CPU round-trip 模拟。
- `TransferEngine.initialize()` 可初始化 Mooncake，但 `_remote_transfer()` 在 Mooncake 存在时直接 `NotImplementedError`，真实 TCP/RDMA path 未落地。
- `transfer_pages()` 创建新的本地 `PagedKVManager`，没有 owner shard incref、borrow/own 标记、RDMA MR、Mooncake Store handle。
- `transfer_async()` 只是线程池调用 `_dispatch_sync()`，没有按 E2P/P2D/A2A/Offload channel 做流式、pull、push_batch 或 prefetch。

### 1.5 EPD workers / vLLM 集成问题

相关文件：

- `core/epd_workers.py`
- `core/epd_pipeline.py`
- `demo/vllm_integration.py`

发现：

- `core/epd_workers.py` 尝试接入 Qwen3-VL real model，但 Prefill 对 DeepStack 的调用依赖具体 HF 内部接口，缺少兼容性探测、版本锁定和 fallback。
- `DecodeWorker.decode()` 只 materialize 全量 KV 到 DynamicCache，再用 HF model 继续 decode；这不是 vLLM PagedAttention block 原地消费，也没有 CoW 写回新增页。
- 旧版 `core/epd_pipeline.py` 仍使用 `encoder_worker.py/prefill_worker.py/decode_worker.py` 的 mock/简化接口，与新版 `core/epd_workers.py` 并存，抽象重复且容易漂移。
- vLLM MooncakeConnector 相关配置生成存在 demo，但没有端到端启动、健康检查、请求路由与真实 P→D 验证。

### 1.6 调度 / Offload / A2A 问题

相关文件：

- `agent/coordination/scheduler.py`
- `agent/coordination/elastic_ratio.py`
- `agent/coordination/offload.py`
- `core/state/anchor_pool.py`

发现：

- Scheduler 是本地启发式 score，没有 RFC §6.14 的 M/M/k 队列模型、rho 阈值、反压、admission control、deadline P99 预测。
- Preemption 当前主要管理 request 对象；没有和真实 decode slot、MooncakeStore、StateLayer lock 串联。
- Offload 同步复制 CPU，缺少非阻塞 DMA、MooncakeStore、状态机、ABORT_DMA、in-place reclamation。
- A2A AnchorPool 是本地 prefix anchor 查找，不等价于 2PC handoff + increment pull + rollback。

## 2. 总体目标与验收标准

### 2.1 工程目标

实现 RFC 的最小可验收 Full System 路径：

1. EPD 三阶段：Encoder → Prefill → Decode 可本地多 GPU 跑通，P→D 能接 vLLM/MooncakeConnector 或明确的 Mooncake transfer adapter。
2. 统一状态对象：版本化 `MultimodalState`、全局 `BlockRef`、页级 refcount/CoW、FeatureBundle refcount、workflow scoped RadixTree。
3. Agent 能力：fork、advance_step、handoff、offload/restore、priority scheduling 具有可测试语义。
4. 跨步骤复用：exact prefix 默认开启；Virtual-RoPE / approximate reuse 在安全闸门与 full recompute fallback 下逐步开启。
5. 可靠性：refcount mismatch、UAF、double-free、orphan block、deadlock 等指标自动化断言。
6. 评估：覆盖 RFC W0-W5 workload 的最小 synthetic/dev-small 版本，报告 TTFT/JCT/reuse/fork/offload/quality/failure 指标。

### 2.2 分阶段验收线

- **P0 通过线**：单机 CPU/CUDA 单元测试全部 pytest 化；状态层版本语义、scope 隔离、FeatureStore refcount、refcount 不泄漏。
- **P1 通过线**：本地多 GPU EPD 跑通；P→D transfer 可替换；测试能比较 single-node baseline vs local EPD。
- **P2 通过线**：Agent fork/advance_step/offload/handoff 的 synthetic 压测通过，UAF/double-free/refcount mismatch 为 0。
- **P3 通过线**：Mooncake/vLLM connector 真实链路打通；没有 RDMA 时 TCP 可跑；RDMA 不可用不影响 correctness。
- **P4 通过线**：W0-W5 dev-small 完成指标报告，满足 RFC §8.9 的基本质量与稳定性约束。

## 阶段 B：状态层语义地基重构（P0/P1，预计 3-5 天）

### B1. 实现 RFC v2 版本化状态对象

任务：

- 扩展 `BlockRef`：
  - `global_block_id: str`
  - `physical_node_id: str`
  - `logical_index: int`
  - `virtual_offset: int = 0`
  - 保留本地 `physical_id` 作为 local backend 字段。
- 扩展 `MultimodalState`：
  - `workflow_id`
  - `step_index`
  - `version_id`
  - `parent_version_id`
  - `snapshot_epoch`
  - `approximate`
  - `status: ACTIVE|OFFLOADING|RESTORING|HANDING_OVER|ABORTED`
  - `ttl_deadline`
- 将 `StateMeta` 中的 workflow/step/ttl 字段逐步提升为 state 顶层字段，保留 `meta` 存 agent/user metadata。
- `fork()` 必须继承父 `snapshot_epoch`，设置 `parent_version_id=parent.version_id`，子版本不可变。
- `advance_step_commit()` 必须创建新 `snapshot_epoch + 1` 或通过 `EpochManager.commit_step()` 生成。

验收：

- 新增 `tests/test_state_versioning.py`：
  - fork 后父状态 advance/decode 不改变子状态 token/kvs。
  - old version release 不影响 child version。
  - snapshot_epoch 单调递增。

### B2. 引入本地 OwnerShard / KV Directory 抽象

任务：

- 新增 `core/control/kv_directory.py`：本地内存版 owner shard，API：
  - `register_block(local_pid, workflow_id, node_id) -> global_block_id`
  - `incref(gid)` / `decref(gid)`
  - `promote_block(gid, node_id) -> PromoteResult`
  - `lease(gid)` / `release_physical(gid)`
  - `commit_epoch(workflow_id, version_id)`
- `PagedKVManager` 不再作为唯一 refcount 权威；本地模式可用 adapter 把 `gid -> physical_id` 映射回 `_pages`。
- 先做 single-process owner shard，保留未来 per-shard Raft/Mooncake backend 插口。

验收：

- fork/refcount/cow 的权威数据来自 KV Directory。
- 128 branch synthetic CoW race：refcount mismatch = 0，UAF = 0，double-free = 0。

### B3. 修复 FeatureStore 生命周期

任务：

- 为 FeatureBundle 引入 `FeatureRef`：`feature_bundle_id/global_id/owner_shard/node_id/refcount/ttl/status`。
- `FeatureStore.incref/release` 实现真实 refcount；refcount > 0 时 LRU 不得删除。
- 实现 RFC §6.9 三段式 hash：
  - L1 URL/path string hash。
  - L2 shape + dtype + resolution + first/last 1KB bytes。
  - L3 full hash async，可更新弱 hash alias。

验收：

- 多 state 共享同一 FeatureBundle，释放任一 state 不删除仍被引用 bundle。
- LRU 只淘汰 refcount=0 的 FeatureBundle。

### B4. 实现 workflow scoped RadixTree

任务：

- RadixTree node 增加 `scope/workflow_id/snapshot_epoch/version_id` metadata。
- `insert(token_ids, refs, scope, epoch, version_id)`。
- `match_longest_prefix(token_ids, scope, epoch)` 只匹配同 workflow 或明确允许的 stable shared namespace。
- 防止不同 workflow 相同 token 但不同图像/不同 feature context 错复用。

验收：

- 新增测试：两个 workflow token 完全相同但 image hash 不同，不得错配 KV。
- `scope` 参数不再被忽略。

## 阶段 C：安全跨步骤复用（P1/P2，预计 4-6 天）

### C1. Exact prefix reuse 正确化

任务：

- `StateLayer.advance_step_prepare()` 改为基于 `workflow_id + snapshot_epoch` 查询。
- exact prefix 返回 refs 时由 owner shard lease/incref，commit 后清理临时 lease。
- 统计 `matched_tokens/matched_pages/saved_prefill_flops`。

验收：

- tail append 场景 bit-exact：启用 exact prefix reuse 与 full prefill logits/KV 对齐。
- Step 2..N TTFT 降低可在 synthetic benchmark 观测。

### C2. Relay/非连续复用降级为“默认关闭的 experimental”

任务：

- 当前 `RelayRecompute` 不具备 RFC 的 correctness 证明，默认关闭。
- 给 `ReusePipeline` 增加 `ReuseDecision`：`EXACT|PROVABLE_VROPE|APPROX_VERIFY|FULL_RECOMPUTE`。
- 非 exact 情况先统一走 `FULL_RECOMPUTE`，保证 correctness baseline。

验收：

- 所有不满足 exact prefix 的情况不会“裸拼接”旧 KV。

### C3. Virtual-RoPE / KV Validity Check 设计落地

任务：

- 在 `BlockRef.virtual_offset` 与 state 版本链基础上实现 VPV 数据结构。
- 先实现 CPU/PyTorch reference attention 验证 Virtual-RoPE 可证条件 C1/C2/C3。
- 设计接口：`analyze_divergence(new_tokens, prev_state) -> {provable, vpv, reason}`。
- 实现 `estimate_attention_drift()` 的 conservative 上界；drift 超阈值必须 full recompute。
- CUDA/vLLM kernel 改造作为后续独立任务，先保证 API 与 reference correctness。

验收：

- 纯追加 + 后缀不变 + mask 不变：reference attention 与 full recompute bit-exact 或在 dtype 容差内。
- middle/head insertion 默认 fallback，除非显式 experimental。

## 阶段 E：EPD real worker 正确性与性能（P1/P2，预计 4-7 天）

### E1. Qwen3-VL worker 兼容层

任务：

- 锁定 transformers/Qwen3-VL API 版本，添加 capability probe。
- `EncoderWorker` 输出 DeepStack FeatureBundle 时记录 feature shapes、目标 LLM layer、dtype/device。

### E2. Decode 不再全量 materialize 作为最终路径

任务：

- 本地 HF decode 可保留为 correctness reference。

验收：

- decode append 产生新 BlockRef，父 state 不被改写。
- fork 后两个分支 decode 首 token 触发 CoW，shared prefix 页 refcount 正确。

## 阶段 F：Agent 协同调度、Offload、A2A（P2，预计 5-8 天）

### F1. Scheduler 引入队列模型与反压

任务：

- WorkerLoad 增加 `arrival_rate/service_rate/rho/p50/p95/p99/deadline_miss`。
- `AgentScheduler` 实现：
  - bounded queue。
  - admission control。
  - high/critical rho 阈值。
  - token bucket 反压。
  - overload 降级序：复用降级 → 压缩升档 → Offload → reject。

### F2. Offload 状态机

## 16. 2026-07-08 新增进展：真实 burst / poisson 压测通过，并补齐 baseline correctness 对比链

### 16.1 新修复：producer 侧“全空 group block 列表被误判 ready”的并发 bug

真实 burst 压测首轮失败时，decode 侧真实崩溃栈最终落在：

- `wait_for_layer_load() -> RuntimeError: P num blocks less than D`

prefill 日志同时出现：

- `local blocks(0) < remote blocks(1) in a KV cache group`

根因：

- `record_send_reqs()` 原先用 `if block_ids:` 判定 producer transfer 是否 ready；
- 在真实 chunked/layered 并发路径中会出现 `block_ids=[[], []]` 这种“group 已创建但尚未拿到真实 block”的中间态；
- `[[], []]` 在 Python 中是 truthy，导致 connector 过早 `ready.set()`；
- consumer 发起 layered receive 时，remote 侧已有目标 block，而 producer 本地仍是空 group，最终触发 `P num blocks less than D` 并打死 decode engine。

修复：

- 改为只有 `block_ids` 中**至少一个 group 含真实 block**时才 `ready.set()`；
- 对 `[[]]` / `[[], []]` 只保留 pending placeholder，不提前宣布 ready。

新增回归：

### 21.2 实现语义

目标是在多模态 Omni 模型中减少重复 Encoder 计算，尤其是 Agent 多轮/多分支场景里的多模态前缀复用。

#### 30.2.2 已确认的 P0 负向热点

1. **多模态缓存哈希成本高于 encoder compute**

   `artifacts/qwen25_omni_dataset_hidden_cache_test_full_gpu2_metrics.json`
   中：

   - `lookups = 1351`；
   - `hit_rate = 0.8786`；
   - `hash_ms_total = 230317.85 ms`，约 `170.48 ms/lookup`；
   - `encoder_compute_ms_total = 59952.82 ms`；
   - `cache_load_ms_total = 275.43 ms`。

   即使命中率已接近 88%，全量 tensor hash 仍消耗约 encoder compute 的
   `3.84x` 时间。当前 hash 路径会把 GPU tensor
   `detach().contiguous().cpu()` 后再转 bytes，属于明确的 TTFT 和吞吐
   P0。

2. **B8 近似复用 / delta-prefill 当前是反向优化**

   `artifacts/rfc_eval_matrix_mm_reuse_20260708.json` 中：

   - B7 TTFT `52.61 ms`；
   - B8 TTFT `149.996 ms`；
   - B8 相对 B7 增加 `97.385 ms`，惩罚 `185.10%`；
   - `delta_prefill_ms_avg = 137.905 ms`；
   - delta-prefill 占 B8 TTFT `91.94%`；
   - penalty 与 delta-prefill 相关系数 `0.9954`。

   因此在完成结构性优化前，B8 不应作为默认在线策略；必须通过收益预测
   gate 决定是否启用，并保留 B7 精确复用路径。

3. **KV transfer descriptor 严重碎片化**

   - RFC matrix：EPD `24889` descriptors / `815562752` bytes /
     `980` EPD grouped batches；
   - paired serving：`30475` descriptors / `998604800` bytes /
     `1330` grouped batches；
   - paired serving 平均 descriptor 仅约 `32 KiB`，每 batch 约 `23`
     descriptors。

   当前数据量接近 1 GB，但产生上千次 batch dispatch、metrics publish 和
   Python 循环，容易放大控制面、锁、系统调用和 transport 固定开销。

4. **缓存未命中时 vision compute 显著**

   paired serving 的 hidden-cache hit rate 仅 `0.2`，vision compute avg
   `219.32 ms`；Agent PD E2E hit rate `0.1667`，vision compute avg
   `254.23 ms`。FeatureHandle 工件已证明命中时可以做到
   `vision_compute_ms_avg == 0`，但端到端收益只有约 `2.66%`，说明
   FeatureHandle 之外仍有较大固定开销。

5. **性能观测本身存在缺口**

   RFC matrix 已传输约 `821 MB`，但报告 `kv_transfer_gbps = 0.0`。
   当前还没有统一拆分：

   - proxy parse/rewrite；
   - admission / queue wait；
   - asset fetch/decode/hash；
   - encoder；
   - prefill；
   - descriptor build；
   - transfer enqueue/wire/ack；
   - decode queue；
   - first-token emit。

   在分阶段计时补齐前，不能把 serving 总延迟归因于单一模块。

### 30.4 Phase 0：建立可归因的真实性能基线

任务：

1. 为每个 request 生成统一 trace/request ID，记录以下 monotonic 时间：
   `proxy_parse`、`proxy_rewrite`、`admission_wait`、`mm_hash`、
   `mm_prefetch_wait`、`encoder`、`prefill_queue`、`prefill_compute`、
   `descriptor_build`、`transfer_queue`、`transfer_wire`、`transfer_ack`、
   `handoff_prepare`、`handoff_commit`、`decode_queue`、

2. 输出 p50/p95/p99、count、bytes、descriptors、backend 和 fallback；
   所有均值必须同时带 count，避免 `count=0` 被误读为 0 ms。
3. 修复 `kv_transfer_gbps=0.0`：带宽只能使用真实 bytes /
   transport elapsed 计算，不能用整个请求时间，也不能在无样本时输出 0
   假装有效。
4. 区分 cold-start、warmup、steady-state；warmup 不进入主报告。
5. 增加每个 stage 的 conservation 校验，确保 stage 时间没有重复计算。
   具体口径：
   - `request_critical_path_ms = first_token_emit_mono - request_received_mono`；
   - 同一进程、同一 monotonic clock domain 的互斥阶段可以直接求和；
   - prefetch/encode、admission、layered transfer 等重叠阶段必须同时输出
     `raw_sum_ms` 和按时间区间求并集得到的 `union_ms`，不得重复计入
     critical path；
   - 跨进程只汇总各自 duration 和因果 span，不直接相减不同进程的
     monotonic timestamp；
   - `unattributed_ms = critical_path_ms - accounted_union_ms`，允许误差为
     `max(2 ms, critical_path_ms * 2%)`，超出即报告
     `stage_conservation_ok=false`。

### 30.5 Phase 1：P0 多模态缓存身份与哈希优化

#### PERF-100：统一 StableContentId

目标：稳定内容身份从请求入口贯穿 Encoder、MMStore、FeatureHandle、
vLLM hidden cache，避免同一图片在每个层级重复全量 tensor hash。

设计：

1. 优先级：
   - 数据集/请求已提供可信内容 SHA256；
   - FeatureHandle `feature_id + model namespace + processor revision`；
   - URL/path metadata key 只作为临时查找键，store 时完成全量校验；
   - 最后才使用 tensor fallback。
2. stable key 必须包含模型、processor、dtype、grid、输出 token 布局等会
   影响 hidden state 的语义字段。
3. 任何 sampled hash 只能作为一级候选索引：
   - cache miss/store 时保存 full digest；
   - 候选命中且身份不充分时执行 full verify；
   - 冲突时按 miss 处理并记录 collision metric。
4. 不能仅因为“更快”而删除现有 full hash；保留为 correctness fallback
   和兼容开关。

修改范围：

- `core/state/vllm_mm_hidden_cache.py`
- `core/state/omni_hidden_prefix_cache.py`
- `core/state/feature_store.py`
- `agent/prefix_cache.py`
- `core/state/mm_store.py`
- FeatureHandle/control payload 定义

测试：

- 相同内容、不同 tensor layout/contiguous 状态得到相同语义 key；
- 不同 grid、processor revision、model namespace 不得碰撞；
- sampled-key 人工碰撞时触发 full verify，不返回错误 hidden state；
- stable-key 命中路径不得调用 full `_tensor_raw_bytes(pixel_values)`；
- cache restart / cross-process key 一致；
- BF16、FP16、FP32、CPU/CUDA 输入覆盖。

性能 gate：

- stable-key 命中路径 `hash p95 <= 10 ms`；
- stable-key 命中路径 GPU→CPU 全量 pixel tensor copy 次数为 0；
- 相同 workload 的 `hash_ms_total / request` 至少下降 `80%`；
- repeat multimodal workload cache hit rate目标 `>= 90%`；
- hit 时 `vision_compute_ms == 0`；
- 输出正确性和 cache collision gate 全通过。

#### PERF-101：缓存锁和部分命中重排优化

1. 将 LRU metadata 更新和 tensor device copy 解耦，锁内不执行大 tensor
   copy。
2. 对部分命中批次减少 `torch.split + torch.cat` 次数，先记录 item
   index map，再一次性组装；未证明等价前不替换原路径。
3. cache metrics 使用线程内累计或无锁 counter 快照，磁盘 flush 不在
   lookup/store 临界区。
4. 增加 singleflight，多个相同 miss 只允许一个 encoder compute。

验收：

- 并发相同图片只发生一次 encoder call；
- `collapsed_waiters/coalesced_waits > 0` 且无死锁；
- cache hit/miss 输出逐 tensor 比对通过；
- lookup lock hold p95 有指标且目标 `< 1 ms`。

### 30.7 Phase 3：P0 KV descriptor 合并与传输流水线

进入传输性能优化前必须先关闭以下正确性/安全前置项，否则不得用该 backend
做吞吐或 TTFT 结论：

- `core/transfer/engine.py` 中 borrowed registration（返回 `-600`）不能由
  当前调用者错误 unregister；
- RDMA-CM receiver 必须具备 peer 认证/授权、地址范围校验、连接超时、
  active-fd 管理、并发/资源上限和可靠 shutdown；
- 显式 iWARP/RDMA 配置必须要求远端 RNIC 地址，禁止默认 loopback；
- real-hardware smoke 必须 opt-in，普通 CI 使用语义测试而不是假设存在
  RDMA 设备。

#### PERF-299：Borrowed registration 生命周期 blocker

1. 将 `register_memory() == -600` 明确建模为 `borrowed=True`，而不是普通
   success；
2. registration handle 记录 owner、borrower 和本调用是否有权
   unregister；
3. borrowed region 的调用者 release 时只减少本地 borrow/ref 记录，
   禁止调用底层 `unregister_memory()`；
4. owner 最后释放且无 in-flight transfer 时才允许 unregister；
5. 增加重复注册、并发借用、owner 先释放、异常取消和 shutdown 测试。

验收：

- borrowed region 不会被非 owner unregister；
- in-flight transfer 期间 MR 始终有效；
- 最终 owner/refcount 收敛且无 registration 泄漏；
- 此 blocker 未通过前，RDMA/peer-buffer 的性能数字只能标记
  `invalid_for_claim=true`。

#### PERF-300：连续 region 合并和 descriptor 复用

1. 在不跨越不连续内存、不同 owner、不同 dtype/layout、不同 lease 的
   前提下，合并相邻 source/destination region。
2. descriptor build 改为预分配/复用数组，减少 Python 对象和 list
   分配。
3. 增加以下指标：
   - descriptors/request；
   - descriptors/MB；
   - batches/request；
   - build_ms；
   - submit_ms；
   - wire_ms；
   - ack_ms；
   - coalesced_regions。
4. 保留原分组算法作为 feature-flag fallback，直到 bit-exact 和异常路径
   全通过。

目标：

- descriptors/MB 至少下降 `2x`，目标 `4x`；
- grouped batches 至少下降 `50%`；
- `descriptor_build_ms p95` 下降 `50%`；
- strict 模式 `fallback_batches == 0`；
- KV bit-exact、输出非空、refcount/lease 收敛。

#### PERF-301：transport-aware 自适应 batching

1. 分别为 SHM、Mooncake TCP、peer-buffer direct、RDMA-CM staged 建立
   `max descriptors / max bytes / max in-flight` profile。
2. 根据历史 transfer p95 和失败率自适应调整，必须有上下限，禁止无限
   放大 batch。
3. `group_delay_ms` 在线默认保持 0；只有明确证据证明能改善 transport
   稳定性时才允许非零，并计入总延迟。
4. retry 只处理可重试错误；参数错误、MR 越界、ownership 错误不得重试。
5. 将每组 `_publish_connector_metrics()` 改为内存累计、周期快照，避免
   batch 数越多 I/O 越多。

#### PERF-302：传输与 layered prefill 重叠

1. 在 layer ready 后尽快异步 enqueue，允许 N 个有界 in-flight group；
2. decode 侧按 layer completion 消费，不必等待全部 descriptor；
3. 使用 event/future 聚合替代每个小 group 的阻塞 wait；
4. 任意失败必须取消后续 group、回收临时 buffer、保持状态机一致。

验收：

- overlap on/off A/B；
- transfer failure injection；
- remote close / timeout / partial completion；
- in-flight buffer 无泄漏；
- p95 TTFT 改善目标 `>= 15%`，TPOT 不回退 `> 5%`。

#### PERF-401：首 token 前事务最小化

1. 分解 prefetch：
   - 必须在 prefill 前完成的数据准备；
   - 可以与 admission/worker selection 并行的工作；
   - 不影响首 token 的后台 publish/metrics。
2. 保持 handoff 原子性，评估 commit 的最早安全点；不能简单把 commit
   移到 yield 之后，否则客户端已收到 token 但状态未提交。
3. 若 commit 仍必须阻塞首 token，则优化 commit 内部目录/WAL 路径，并
   明确计入 `handoff_commit_ms`。

QA 与状态断言：

- commit 成功后才允许发送第一个用户可见 token；状态应为
  `HANDOFF_COMMITTED/DECODING`；
- commit 失败且尚未发送首 token：执行 rollback，返回明确 5xx，状态为
  `ROLLED_BACK/FAILED`；
- decode 在首 token 前失败：执行 rollback，不得残留 ACTIVE lease；
- 首 token 已发送后的下游断连：不得把已提交 handoff 回滚成旧 owner，
  应进入 finish/cancel 清理路径；
- commit 超时不得重复提交产生双 owner；重试必须幂等；
- 记录 `commit_before_first_token=true`、`handoff_commit_ms` 和最终状态。

性能 gate：

- 在保持上述状态断言的前提下，`handoff_prepare + commit` p95 目标
  `< 5 ms`；
- 若真实 KV directory/RDMA 环境无法达到该目标，报告实际值和占比，
  不得通过把 commit 移到首 token 之后规避。

#### PERF-402：WAL 和 metrics 有界异步写

1. `JsonLineWAL` 增加可配置模式：
   - `strict`：每条 flush + fsync，保持当前语义；
   - `group_commit`：单 writer、有界队列、最大 batch 数和最大
     durability window；
   - `memory/test` 只用于明确非生产环境。
2. 状态转换成功的定义必须与配置的 durability SLA 一致，不能在 WAL
   实际不可恢复时提前宣告 durable。
3. shutdown、异常和 fork 后正确 flush；队列满不得静默丢 WAL。
4. metrics/trace 可 drop 或采样，但必须有 dropped counter；WAL 不可
   drop。

性能 gate：

- metrics/trace 热路径 p95 `< 1 ms`；
- group-commit durability window 建议上限 `10 ms`，最终由故障恢复测试
  决定；
- kill -9 / restart 后 handoff/offload 状态可恢复；
- strict 模式行为与当前实现一致。

### 30.9 Phase 5：P1 缓存预取、队列和调度

#### PERF-501：SLA-aware pool spillover

2. score 同时考虑 queue、rho、service rate、预计 prefill/decode cost、

3. high-prefill pool 过载时允许 hybrid/非 strict 请求 spillover；
4. 输出 `strict_pool_hit / affinity_override / load_spillover /

验收：

- 混合 workload 下同类 worker load max/min 目标 `<= 1.5`；
- TTFT p95 下降且 SLA miss 不增加；
- 显式 strict target 不被 spillover；
- scheduler 单测覆盖“高偏好但已负载”和“空闲普通池”。

### 31.3 已确认的本地热路径缺陷

1. `_build_transfer_params_for_group()` 已按完成的 layer group 产生 slice，
   `_send_blocks()` 又依据全局注册层数推导 group size，导致同一 layer slice 被
   二次拆分并执行多次同步 transfer。
2. `group_delay_ms` 同时位于 group dispatch 和外层 chunk 循环，形成重复 sleep，
   且旧逻辑会在单组/最后一组后等待，直接扩大 TTFT。
3. 任何非零错误都会递归拆分重试；invalid MR、越界、ownership/lease/layout
   错误无法靠重试修复，只会放大尾延迟和故障风暴。
4. TCP、Mooncake RDMA、RDMA-CM/iWARP 共用静态 descriptor 默认值，未体现不同
   transport posting/connection/rail 特征。
5. 只有单请求真实 EPD gate，缺少可对同一数据集端点执行 warmup 排除和并发矩阵
   的通用 benchmark。

### 31.4 PERF-301A：安全拆批与错误分类（本轮已实现）

改动范围：

- `core/control/vllm_mooncake_connector.py`
  - layer-scoped descriptor 在未超过 transport cap 时只提交一个物理 batch；
  - 超过 cap 时只按 `max_transfer_descriptors/max_transfer_bytes` 拆分；
  - `group_delay_ms` 只发生在相邻 transport chunks 之间；
  - terminal failure 单次计数，retry attempt 与 terminal batch 指标分离；
  - TCP/direct 默认 descriptor cap 从 32 调整为真实标定支持的 64；
  - RDMA/RDMA-CM/iWARP 默认 128，但仍必须由真实跨机 profile 复核；显式配置优先。
- `core/control/vllm_transfer_primitives.py`
  - 新增保守 transient/non-retryable 分类；未知错误默认 fail-fast；
  - timeout、EAGAIN/EBUSY、连接重置/拒绝、网络不可达、ENOBUFS 等允许有界重试；
  - 非法 buffer/address、未注册 MR、越界、ownership/permission/lease、layout/

### 31.7 后续创新迭代顺序

#### PERF-302B：capability-gated bounded async overlap

- 按 `backend+peer+rail` 建立独立 credit semaphore；禁止全局无界 future。
- submit 返回 handle 后才允许下一 layer group 计算/传输重叠；completion 必须
  驱动 buffer/MR refcount 释放。
- cancellation、timeout、peer failure 必须 drain/abort handle；shutdown gate 要求
  `active_registrations=0`、`inflight=0`、`illegal_unregisters=0`。
- TCP 默认关闭：本机真实 async scratch 中 async submit 本身约占完整传输时间，
  p95 不优于 sync；只有 RDMA/iWARP 三轮数据通过才开启。

#### PERF-303：KV cache group identity 与 stride descriptor

- 对照最新 vLLM，避免把 hybrid/HMA cache groups 扁平化后丢失 group identity；
- 先添加多 group/null-padding/不同 page size 的 bit-exact 与 ownership 测试；
- 连续同 path、同 provenance、同 lease、物理相邻才允许 merge/stride；
- 不跨 routing path、MR owner、layer group 或 security boundary 合并。

#### PERF-304：transport-aware 自适应批大小

- profile key：`backend, protocol, peer, device/rail, payload bucket`；
- 初始值 TCP=64、RDMA=128，hard min/max 和 byte cap 不可突破；
- 仅在有足够样本时依据 p95/throughput 做缓慢调整，错误/timeout 立即降档；
- profile 有版本和 TTL；冷启动、peer 变化、RNIC reset 后回到安全默认；
- 通过 feature flag 回滚到静态批大小。

#### PERF-305：sender posting 并发与多 rail

- 分别 A/B `num_workers`、sender task 数、每 rail queue depth；
- 监控 CPU、context switch、socket/RDMA error、p95，不以平均 Gbps 单指标决策；
- iWARP、RoCE/IB、TCP 分开标定；`protocol=rdma` 不能作为真实 RNIC 使用证明，
  必须记录 provider/device/QP/rail 与网络计数器。

### 32.1 本轮结论与状态

本轮 A/B 只用于工程热路径判断，不作为 GPU-normalized 成本结论。vLLM 官方也明确
P/D disaggregation 的首要目标是分别控制 TTFT/ITL，并不保证天然提高吞吐。

### 32.2 已完成实现

1. **E→P 直接落最终 Tensor**
   - `TransferEngine.read_remote_peer_buffers_into_tensors()` 直接注册最终 Tensor 并批量
     读取，移除 managed buffer→Python bytes→CPU→GPU 的重复拷贝；
   - 注册区遵循 owned/borrowed/refcount/inflight 语义；
   - `FeatureHandleProvider` 增加 content/model/device keyed 有界 resolved LRU、进程级
     singleton、单 Tensor 无额外 `cat` 快路径。
2. **Prefill-owned Direct FeatureHandle 缓存**
   - Proxy 增加 entries/bytes/TTL 三重上限的 LRU；
   - 相同 feature-set 并发 miss 通过 singleflight 合并；
   - eviction/expiry/shutdown 才释放真实目标 buffer，不能被 vLLM MM cache eviction
     提前破坏；
   - 指标包含 hit/miss/store/eviction/expired/inflight/bytes。
3. **Prompt-only Prefill/Decode 重叠与连接池治理**
   - 已知 KV topology 后可提前打开 Decode stream；
   - keepalive expiry 必须小于上游 Uvicorn keepalive，实验配置由 30 s 修正为 4 s；
   - Prefill 502 必须输出异常类型，禁止空错误信息。
4. **语义 Prefill Render 缓存（实验开关，默认关闭）**
   - 缓存的是 vLLM processor/render 中间结果，不是模型回答；

## 33. 2026-08-30 PERF-302E：Decode 特征去重事务、worker epoch fence 与严格恢复

### 33.1 目标、状态与不可妥协约束

本阶段针对 prerendered Decode 请求中重复序列化 14--16 MiB 视觉特征的问题，开发
`full -> hash-only` 协议，并补齐 worker 重启、流中断、缓存归属和可用性检查。当前
P0/P1 功能已实现并完成真实 Qwen3-VL EPD 验证；通用配置仍保持默认关闭，只在明确
启用 prerendered Decode、严格 no-fallback 和 epoch monitor 的性能 profile 中开启。

约束：

1. hash-only 只能引用同一 Decode worker、同一进程 incarnation 已成功消费的特征；
2. streaming 请求只有收到合法终态 `[DONE]` 才能晋升 warm，首包不代表事务成功；
3. epoch 不可确认、worker 不可达或进程变化时必须发送完整特征，禁止猜测命中；
4. 失败不能在同一请求内 silent fallback，避免非幂等流重复执行；
5. 所有性能结论必须来自真实模型、真实图像、真实 SSE 和真实 Mooncake/vLLM 路径。

## 34. PERF-302J：vLLM UUID 兼容的 Client→EPD 多模态轻量引用

### 34.1 证据与目标

r10--r12 的正式窗口中 `proxy_parse p95=194--236 ms`、max=426--568 ms。真实 dataset
请求体为 0.13--3.78 MB，10 个样本合计约 7.98 MB；本机微基准虽显示 `msgspec`
可把 4 并发纯 JSON decode 从约 9.65 降到 4.07 ms，但这不足以解释数百毫秒尾部，
主因仍是重复 data URL 的序列化、上传、收包和解析。

vLLM 上游已定义 media `uuid` 缓存协议：首次请求发送真实媒体并携带稳定 UUID；命中后
可将媒体字段置空，只发送 UUID；UUID 冷 miss 必须失败。本阶段复用该 wire semantics，
将它扩展到 EPD 自有的 E→P direct feature handle、Prefill render 和 Decode MM cache，
避免另造不兼容私有协议。

### 34.2 开发步骤

1. Proxy 增加默认关闭的 `--enable-client-mm-uuid-references`，并透传到 E2E 配置生成器；
2. `ServingControlPlane` 在 media item 携带 UUID 时以“modality + UUID”生成稳定内部 key，
   使 full 与 `image_url=null` 请求保持同一身份；无 UUID 仍保留内容 hash 语义；
3. render cache digest 对 full/compact media 做同一占位归一化，确保首次 full render 后
   compact 请求不再把空媒体发给 Prefill renderer；
4. direct feature handle 或 render cache 任一冷 miss 时 fail closed，禁止把空媒体静默发给
   Encoder/Prefill；记录 full/compact/mixed、item 数、冷 miss 与请求体字节 metrics；
5. 响应头明确返回 `X-EPD-Client-MM-UUID-Mode`，benchmark 记录实际模式；
6. benchmark 增加严格 UUID 模式：warmup 为每个真实媒体赋稳定 UUID 并发送 full，正式
   窗口置空媒体字段；要求每条成功请求均为 compact，metrics compact delta 等于正式

## 37. PERF-302O/P：轻量 incarnation、请求级 epoch fence 与后台一致性窗口

### 37.1 本轮审查结论与实施顺序

双 Decode 的主要新瓶颈不是 Encoder 或 sub-ms handoff，而是 Decode cache 的进程代次控制面：
旧实现把约 57 KB 的 Prometheus `/metrics` 当作每请求 epoch fence；高并发时，同步 probe
与 Generate 共用忙 worker 的 HTTP/event-loop 资源，probe 超时会把健康 worker 摘除并清空
其整代 hash cache。按“先正确性、再控制面、最后数据面分组”的顺序完成以下工作：

1. **PERF-302O-1（完成）**：通过 vLLM 官方 `--middleware` 接口增加
   `/mooncake_epd/incarnation`，返回 60-byte 进程生命周期 token，不修改 site-packages；
2. **PERF-302O-2（完成）**：Proxy 支持独立 epoch endpoint，记录 response bytes、延迟与
   source；Prefill/Decode 生成器和 E2E evidence 全链路透传；
3. **PERF-302O-3（完成）**：hash-only lease 附带期望 incarnation；Decode middleware 在
   进入 Generate/engine 前比较 token，不一致返回 409，失败请求不重试、不 fallback；
4. **PERF-302O-4（完成）**：409 响应中的实际 incarnation 被代理原子学习，同时只失效
   对应 Decode worker 的旧代 warm hash，避免“全量重热成功后下一次 compact 再失败”；
5. **PERF-302P-1（完成并晋级本机 profile）**：在请求级硬栅栏成立后使用 1 s 后台 probe
   + 2 s observation window，正常请求复用后台观测，竞态仍由 Generate 前 fence 兜底；
6. **PERF-302P-2（完成，不晋级）**：评估 static pipeline credit=4、freshness=50 ms 与
   `layers_per_group=8`；均未同时改善吞吐、TTFT 和 strict goodput；
7. **PERF-302P-3（下一轮）**：将 2 s 常数升级为 guard-aware 自适应窗口：按后台 probe
   实测 p99、poll jitter 与 worker health 决定窗口，设置上下界并保留显式 0 配置；
8. **PERF-302P-4（下一轮）**：为 Prefill direct endpoint 引入 incarnation/租约，Encoder
   的远端 segment cache 必须按 Prefill 代次失效；滚动升级编排要在 Prefill 与 Encoder
   之间建立同代门禁，不再依赖手工清理 rpc_meta。

## 38. PERF-302Q：E→P / P→D 双代次协议与无 Decode 重启恢复

### 38.1 缺陷模型与目标

滚动 Prefill 会同时改变两类进程内状态：Encoder→Prefill direct peer-buffer 注册，以及
Prefill→Decode Mooncake bootstrap worker/ZMQ 地址。稳定 `engine_id=epd-prefill` 是目录身份，
不能充当进程代次。旧实现因此出现两种真实故障：长期 Encoder publish `rc=-1`；长期 Decode
继续使用 `_remote_agents[engine_id]` 的旧 worker address，直到 ZMQ receive timeout，请求挂死。

本轮目标是建立显式 process-incarnation 协议：稳定逻辑 ID 保留，所有含进程内指针、注册或
bootstrap 地址的缓存都按 opaque incarnation 分代；变代时只失效目标 Prefill，不重启 Decode、
不回退 TCP/store、不重复视觉编码。

### 38.2 E→P direct engine coordinator（完成）

Encoder direct engine 已改为 generation/lease coordinator：正常 publish 并发执行；发现同一
remote session 的 Prefill incarnation 改变时，停止发新 lease、等待在途 lease 排空、关闭旧
TransferEngine、原进程创建并初始化新 engine。只对精确的 peer-buffer transfer rc failure
允许一次同后端 reactive recovery；不 fallback，重试位于 feature bundle 之后，不重复编码。

真实 A/B 工件 `epd_prefill_incarnation_direct_recovery_summary.json`：Encoder PID 3406569
不变，Prefill token 改变；A/B 均传输 122,093,592 bytes，B 首次 publish generation 1→2、
`proactive_incarnation`、无 reactive retry/fallback。随后 5/5 稳态 E→P HTTP 200，publish
median 224.39 ms、p95 340.02 ms、median 0.5441 GB/s。

### 38.3 P→D bootstrap topology fence（完成）

Prefill scheduler response 新增 `remote_engine_incarnation`；Proxy 的 topology normalization/
cache/pipeline 保留该字段；Decode scheduler metadata 聚合 engine→incarnation。Decode worker
不跨线程直接改上游缓存，而是在 receiver event loop 的 `_start_load_kv` 前执行 fence：

1. 首次观察只记录 token，重复 token 为常数时间；
2. token 改变时等待同 bootstrap URL 的旧 singleflight query 完成；
3. 只删除该 engine 的 `_remote_agents` 与 `_tp_size`；
4. 复用上游 `handle_new_engine_id` 重新发现 worker 地址；
5. 缺 token 保持旧版兼容，冲突 token fail closed。

## 39. PERF-302R：Proxy→Prefill direct-handle 代次栅栏与无 Proxy 重启恢复

### 39.1 已完成实现

上一阶段真机证明：Prefill 重启后，长期 Proxy 中的 `epd-direct://` handle 仍指向旧进程
peer-buffer；即使 Encoder 和 Decode 均已按新代恢复，新 Prefill EngineCore 读取旧地址仍会
`rc=-1` 并按 strict 模式退出。本阶段把临时“Prefill 后滚动 Proxy”替换为产品协议：

1. Prefill launcher 通过 vLLM 官方 `--middleware` 暴露 60-byte

### 39.8 PERF-302R-6：语义 sideband、CUDA 生命周期屏障与自适应直读（完成）

#### 39.8.1 根因和实现

`image_grid_thw` 只有 24 bytes，却与四个约 30 MiB 的视觉 hidden tensor 一起进入 GPU
register/read/unregister 生命周期。远端 read 返回后立即 unregister，既缺少显式 device
visibility barrier，又把 vLLM 原本 `keep_on_cpu=True` 的语义字段留在 CUDA 域；重启和 managed
read 场景可把后续 split 计算污染为 0。

修复遵循“不删除 bulk 传输逻辑、缩小语义字段风险域”的原则：

1. `FeatureBundleDescriptor.metadata` 新增权威 `grid_thw_values` 和 `spatial_merge_size`；
2. Prefill 从 control sideband 重建 CPU `int64 image_grid_thw`，校验整数/有限/正值、shape、
   nbytes、`sum(split_sizes)` 以及 spatial-merge 后行数；
3. sideband 存在时不远程读取 24-byte grid，代表性请求 descriptor 5→4、bytes
   122,093,592→122,093,568；四个 bulk hidden tensor 仍走真实 Mooncake direct read；
4. registered destination 在 unregister 前执行 CUDA device visibility barrier，并记录
   `visibility_sync_ms`；
5. 兼容旧 descriptor：没有 sideband 时仍读取 grid，但在进入模型前执行相同语义校验；
6. trace 增加 grid source/device/values，便于区分 control 语义和 bulk DMA。

随后新增三态策略 `registered_tensor | managed_buffer | adaptive`。生产默认配置为 adaptive：
先使用低干扰下更快的 registered path；某次已完成 registered read 总耗时达到 750 ms 时，
**只让未来 8 次读取**进入 managed-buffer cooldown，结束后再做 registered probe。不重试当前
用户请求，避免双读和掩盖数据一致性错误。所有状态转换加锁并进入 trace。

### 39.9 PERF-302R-7：按 peer/payload bucket 的 EWMA 自适应直读（完成）

固定 750 ms 阈值对当前约 120 MiB feature 有效，但对未来小图、多图或不同视觉模型不能保持
相同含义：小 payload 即使有效带宽严重下降也可能永远达不到 750 ms，大 payload 则可能被
误判。因此本阶段在绝对阈值外增加负载归一化基线：

1. policy state 按 `remote_session × power-of-two nbytes bucket` 隔离，一个 Encoder peer 或
   大图桶的抖动不会把其他 peer/负载一起切到 managed；
2. registered fast completion 以 `ms/MiB` 建立 EWMA，生产 `min_samples=4`、`alpha=0.25`、
   `slow_ratio=3.0`；
3. 只有达到最小样本且当前 normalized latency 超过基线倍数，或超过 750 ms 绝对上限时才
   进入 cooldown；慢样本不更新 EWMA，避免持续拥塞把异常学习成正常；
4. 状态采用最多 32 个 bucket 的 LRU；并发选择/观察由同一锁保护；已开始的请求不被回溯
   切换，也不做 same-request 双读；
5. trace 增加 policy key、payload MiB、effective MiB/s、normalized latency、baseline/sample、
   relative threshold、slow reason 和 transition。

软件验证：新增归一化 EWMA、慢样本不污染、peer 隔离、bucket 隔离回归；provider `14 passed`，

### 39.12 PERF-303：重算价值/字节感知的抗扫描 Encoder 缓存（完成）

#### 39.12.1 问题与设计

4 GiB/32-entry 内容缓存仍使用纯 LRU。Agent 多轮与多模态检索常见“少量热点图像 + 大量一次性
扫描”：热点虽已复用，但只要 32 个更新的冷对象进入就会全部逐出，下一轮重新执行视觉塔，直接
抬高 TTFT 并占用 E-stage 吞吐。本阶段增加可选 `reuse_density` 策略：

1. 每次 exact-content lookup 进入有界频率历史，最多 `max(64, 8×max_entries)` 个 key；
2. 每 `max(100, 10×max_entries)` 次 lookup 将频率减半，避免历史热点永久占用；resident key 在
   ghost history 裁剪时受保护，但仍会随全局 aging 降权；
3. Qwen3-VL 不为准入强制 CUDA synchronize。重算工作量使用稳定的 visual output rows，score 为
   `decayed_frequency × visual_rows / bundle_bytes`；host encode ms 只反映 kernel enqueue，不能
   作为 GPU 重算成本；
4. 有空位时首个精确结果直接入缓存；压力时只选择未 refcount/lease 的最低 score resident，候选
   低于所需 victim 的最高 score 时 bypass cache；singleflight 计算结果仍返回当前请求，不因拒绝
   缓存而失败；
5. `lru` 保持可选回退，但两种策略都严格拒绝单条 oversize 和 pinned 条目导致的不可腾挪写入，
   不再允许超过 max bytes/entries；
6. health 新增 admissions/rejections、value evictions、frequency resets/history、largest entry、
   pinned/leased bytes；response 显式区分 true cache hit、singleflight waiter 与本次 admission，
   benchmark 不再用 `encode_ms==0` 猜命中。

审查同时修复：dynamic batch runner 在关闭时显式取消被 queue capacity 阻塞的 put task，并失败
所有已提交 future，避免 drain 后 putter 再入队；benchmark 只允许停止 listener cmdline 与整个
process-group 成员列表能证明属于本项目 launcher 的进程，不再假设 PGID leader `/proc` 必然存在；
`/describe` 只允许 direct backend，未 publish ticket 由 60 s TTL 后台 sweep 与请求前 sweep 双重
回收，health 暴露 expired；`/encode` 和 `/describe` 均返回真实 hit/singleflight/admission outcome。
Encoder 继续接受 data URL；本地文件需 allowed root，HTTP 即使设置旧 enable/host allowlist 也
fail closed，直到实现把连接固定到已验证 IP 且保持 TLS SNI/Host 语义的 transport，避免 DNS
preflight 与 HTTP client 二次解析之间的 rebinding。外部 GPU5 llama-server 始终未被停止。

## 39.16 PERF-309：压力门控 Ready-credit Singleton ViT 调度（已晋级）

### 39.16.1 选择依据与明确排除项

PERF-308 treatment 的三对 stage trace 显示，C1/C4/C8 `mm_prepare` p50 中位约为
1.04/2.54/11.56 s，已经远大于 admission/control bookkeeping；C8 仍是首要 TTFT 瓶颈。
当前 Encoder 在 dynamic batch 关闭时，每个请求通过 `asyncio.to_thread(worker.encode)` 向同一
GPU5 vision model 并发提交；请求进入 GPU 的顺序取决于 CPU processor 完成和线程调度，没有
patch cost、queue age 或 deadline 信号。

本阶段不重新包装已经否定的方案：PERF-302R-8 的 packed batch=2 在真实 C8 中虽然 p95
-9.74%，但 throughput -6.40%，因此不能简单把旧 dynamic batcher 默认打开。PERF-309 先隔离
验证 **singleton dispatch**（`encode_many` 的 batch-of-one，不拼 tensor）是否通过减少并发 host
submission/默认 stream 争用获得收益；只有真实能力门通过，才实现 patch-aware 重排。

外部依据与当前代码方向一致：SGLang runtime 使用有界执行背压但 pending count 仍不表达异构
视觉成本；TCM-Serve 以 preprocessing/encoder/prefill/token footprint 做分级与 aging；RServe 以
multimodal token 阈值形成批次；NVIDIA Dynamo 把 parallel decode、embedding cache、MM KV
routing 和 Encoder disaggregation 分开。当前项目已完成前处理并行、内容缓存和 EPD，下一项应是
视觉 patch/token 感知的调度，而不是继续微调已经出现收益递减的 TCP submit batch。

### 39.16.2 两阶段实施

**阶段 A：无代码语义变化的能力门。**

   正信号，停止该分支并保留负结果，不实现新调度器；
4. runner 必须复用 exact listener/PGID/member 校验，不能使用旧脚本中仅按端口杀进程的逻辑；

**阶段 B：仅在能力门通过后实现 `_Qwen3PatchAwareDispatcher`。**

## 39.17 PERF-310：有界 Patch-aware Aging Singleton 调度（实现完成，4 秒候选待三对晋级验证）

### 39.17.1 目标、边界与实现

在 PERF-309 已晋级的 pressure-only singleton dispatcher 上增加 opt-in `patch_aging` 策略，目标是
让已经进入同一 Encoder 队列的小 patch 请求绕过尚未执行的大 patch 请求，从而降低 head-of-line
blocking；同时用 aging 上限保护大图，避免把 SJF 变成无界饥饿。生产 launcher 默认仍为 `fifo`，
只有真实 balanced A/B 全部门禁通过后才允许改变默认值。

实现保持以下硬边界：

1. 只支持 `max_batch_size=1`，否则配置 fail closed；不重新引入 packed ViT batch；
2. 每次选择只同步扫描 FIFO head 与至多 `reorder_window=8` 个当前 ready item，选择期间无 `await`；
3. 未选 item 在同一 event-loop tick 内执行 `task_done()+put_nowait()`，保持 bounded Queue 容量与
   unfinished-task 守恒；cancelled item 被显式跳过；
4. oldest wait 达到 `starvation_ms` 时优先 oldest，否则按 `(patch_count, enqueued_at)` 稳定选择；
5. queue wait 与 encode latency 样本使用 `deque(maxlen=2048)`，health 暴露 scan/reorder/aging
   override、patch bucket、queue wait 和 batch encode p50/p95/p99/max；
6. close/cancel 仍等待已经开始的 native/CUDA work，最终 ticket、pending、native inflight 必须归零。

真实 W0 80 样本经真实 Qwen3 processor 统计得到 patch 范围 256--18012、26 个唯一值；据此构建
`perf310-w0-patch-mix.jsonl`：16 个真实唯一样本，每个 C8 burst 固定 4 个 large 在前、4 个 small
在后，large 为 15400--18012 patches，small 为 256--280 patches。无 mock。

软件验证：patch-aware ready selection、FIFO 保序、starvation override、window 边界、cancel skip、
配置 fail closed 与 health 暴露均有回归；targeted `17 passed, 37 deselected`，完整 Encoder 文件
`54 passed`，py_compile、Ruff、bash-n 通过。独立架构复审为 APPROVE，无 HIGH/MEDIUM；仅记录一个
低风险测试调度顺序敏感项，若 CI 出现 flake 再用显式 admission barrier 加固。
