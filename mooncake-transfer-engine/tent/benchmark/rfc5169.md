# [TENT] Pipeline slice submission and reuse request metadata

Implements the remaining requirements of RFC [#5169](https://github.com/kvcache-ai/Mooncake/issues/5169)
on top of the upstream pipeline and the explicitly imported preparation/completion
dependencies. This file is the English PR description, design note and results
template; it makes no unmeasured bandwidth claim.

## Description and design (written before implementation)

The starting main already includes Phase 1 from #5277. This branch imports the
open #4779 completion-counter and #4782 SelectionResult-cache implementations
as explicit prerequisites, then extends them in separate Phase 1 and Phase 2
commits. Classic TE and public Request/TransferEngine APIs remain unchanged.

| Upstream work checked before coding | State at import | Revision / use |
| --- | --- | --- |
| [#5039](https://github.com/kvcache-ai/Mooncake/pull/5039) | Merged | Reviewed the classic TE seal race and error handling; classic TE is unchanged. |
| [#5277](https://github.com/kvcache-ai/Mooncake/pull/5277) | Merged | Existing TENT pipeline in base main `504f2ae`; extended rather than duplicated. |
| [#4779](https://github.com/kvcache-ai/Mooncake/pull/4779) | Open | Imported `e5df131d2575dad88c279fffa31f0835aacad21e` as a prerequisite. |
| [#4782](https://github.com/kvcache-ai/Mooncake/pull/4782) | Open | Imported `56ce5782438020719d711652fdfb429b7b60d027` as a prerequisite. |

Phase 1 flushes each lane at its watermark, including within a large request.
The slice plan determines the final task slice count **before** its first slice
is published; that count is immutable afterwards. Consequently an early chunk
cannot win the last-slice CAS or increment #4779's finished counter while a tail
still needs construction/publication. Each built slice owns one task reference;
the batch owns another until free. Runtime submit/poll use the existing batch
progress lock, including runtime-queue and progress-worker modes, so partially
installed public task maps cannot be observed as a completed batch.

After accepting any prefix, submission returns OK and reports enqueue failures
through the rejected slices' normal terminal status path. It releases only their
device charges and never retries the accepted prefix as a group. All slices,
accepted or rejected, stay in the batch-owned chains until reclamation. Existing
slice CAS and ownership counters prevent duplicate completion/release.

Workers prepare a bounded number of slices before posting and returning to CQ
polling. A cursor retains an oversized dequeued chain without modifying its
batch-owned links. Endpoint QP/CQ credit reservation, partial-post handling and
periodic/chain-tail signaling stay unchanged. Opt-in deadline arbitration keeps
its existing whole-round ordering semantics.

Phase 2 extends #4782 with consecutive same-MR boundary reuse and fewer temporary
owner/task allocations. Cache hits must reproduce findBuffer's first covering
buffer, including overlapping registrations, zero length and overflow handling.
Missing remote ranges still invalidate and retry the entire target group.
Selection cache keys, generation invalidation, hint validation and merge limits
remain those of #4782 and current main.

## Invariants and regression coverage

| Invariant | Evidence |
| --- | --- |
| No task/counter completion before all planned slices exist and resolve | `FirstChunkCompletesBeforeTailConstruction` stops the producer inside its first flush, completes that chunk, and checks PENDING, the final slice count, references and an unchanged completion counter before releasing the tail. |
| A rejected suffix never replays or loses an accepted prefix | `RejectedTailSettlesAnAlreadyPublishedTask` injects rejection within one task and repeats completion to check the CAS; `AcceptedPrefixIsNotReplayedWhenLaterChunkIsRejected` checks a partially accepted batch, device charges, unique slices and references. |
| Batch completion waits for the tail with either runtime/progress mechanism | `CompletedPrefixCannotCompleteBatchBeforeTail` covers runtime queue ON/OFF crossed with progress worker ON/OFF. The direct RDMA producer/consumer race is tested separately above. |
| Worker preparation is bounded and credits/signaling remain correct | `WorkerBoundsAnOversizedDequeuedChain` exercises the retained cursor. Existing `BoundedPreparationPostsFullCreditAndKeepsTheTail`, selective-signaling, partial-post and quota tests exercise real worker/endpoint code with fake verbs. |
| Same-MR reuse preserves validation, merging and first-covering MR identity | `CachedBoundariesMatchFirstCoveringMr` compares actual boundary resolution with `findBuffer` across adjacent/overlapping MRs, zero length, crossing ranges and address overflow. Existing merge and #4782 route-cache tests cover policy keys, generation changes, UNSPEC and merge ON/OFF. |
| Optional tracing counts only accepted data posts | `TransferTraceRecordsOnlyAcceptedDataWrPosts` injects a partial `ibv_post_send` failure and checks accepted/rejected traces with tracing OFF and ON. Runtime smoke checks exercise caller completion reporting without a NIC. |

## Reproduction

Build both `tent-rfc5169-deps` (before) and the final branch (after) with
`USE_TENT=ON`. Use identical compilers, Release flags, configurations, NICs and
CPU placement. A separate worktree/build directory avoids mixing libraries.

```bash
cmake -S . -B build-tent -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DUSE_TENT=ON -DUSE_CUDA=OFF -DBUILD_UNIT_TESTS=ON \
  -DWITH_STORE=OFF -DWITH_STORE_RUST=OFF -DBUILD_BENCHMARK=ON \
  -DPython3_EXECUTABLE=/usr/bin/python3
cmake --build build-tent --parallel 2
# Start the repo's HTTP metadata server in another terminal using a Python
# environment with aiohttp. Substitute an available loopback port for PORT:
# python python/mooncake/http_metadata_server.py --host 127.0.0.1 --port PORT
MC_METADATA_SERVER=http://127.0.0.1:PORT/metadata \
  ctest --test-dir build-tent/mooncake-transfer-engine \
    --output-on-failure --timeout 180 -j 1
```

Local validation additionally set
`-DPython3_INCLUDE_DIR=/usr/include/python3.12` to replace a cached interpreter's
headers. Fresh builds should discover development headers matching their chosen
Python executable. Stop the temporary metadata server after testing.

The tracing regressions were also run with `MC_USE_TENT=1
MC_TENT_TRACE_TRANSFER=1`, filtering `tent_rdma_transport_test` to
`RdmaWorkersSharedQpTest.TransferTraceRecordsOnlyAcceptedDataWrPosts` and
`tent_runtime_queue_dispatch_test` to
`RuntimeQueueDispatch.CompletedPrefixCannotCompleteBatchBeforeTail`.

The new knob is `transports/rdma/workers/submit_chunk_size` (slices per lane).
Its default `0` inherits `endpoint.max_qp_wr`; the first publication per lane
uses `ceil(chunk_size / num_lanes)`, matching upstream's default startup ramp.
Positive values set the steady caller watermark and worker preparation budget;
negative values are rejected. Block size, lanes, runtime queue, progress worker,
QP/CQ limits, signal interval and deadline arbitration defaults are unchanged.

On the target node, start a native `tebench --backend=tent --xport_type=rdma
--seg_type=DRAM --total_buffer_size=2147483648` server with `MC_USE_TENT=1` and
`MC_TENT_CONF` pointing to the same base config with the desired lane count.
Record the segment name it prints. Run each lane count separately if only one
target server is available; otherwise pass the matching server segment for each
lane count. Preserve the effective target configs alongside the initiator's
generated configs and raw logs. The config must use routable RPC hostnames on
both nodes, and available RDMA devices.

```bash
python3 mooncake-transfer-engine/tent/benchmark/rfc5169_bench.py \
  --tebench build-tent/mooncake-transfer-engine/benchmark/tebench \
  --config tent-conf.json --out results/after --label after-COMMIT \
  --target-2 TARGET_2 --target-8 TARGET_8
```

Repeat for the before checkout and use a separate output directory. Batch 128
is the no-regression check. The script sets `MC_USE_TENT=1`, records each command
and effective config, and disables merging **only for this benchmark** because
native tebench otherwise merges its contiguous descriptors. Use the RFC's QP/CQ
limits and signal interval in the base config to compare its workload; the
script changes only lane count and merging. Use `--dry-run` to inspect the entire
matrix without requiring RDMA hardware.

`MC_TENT_TRACE_TRANSFER=1` (read once per process) enables JSONL records prefixed
with `TENT_TRACE` on stderr. `--trace` makes a separate instrumented sweep; use
uninstrumented runs for bandwidth/no-regression claims. Every accepted submit
interval observed terminal through the batch-status API emits once. Failed
submits before acceptance are not traced. Absent enqueue/post timestamps are
JSON null, not synthetic latency measurements. Partial successful hardware
posts contribute only their accepted WRs. Concurrent lanes use atomic minimum
and maximum timestamps.
The prerequisite baseline predates these trace points. Before filling its
timing cells, backport the same tracing-only instrumentation without the
pipeline/MR changes; an uninstrumented baseline cannot produce those columns.
This backport and the hardware timing A/B remain unverified here.

The C++ interval starts at TENT `submitTransfer` entry and ends when the caller
observes a terminal batch status; runtime prepare measures `prepareSubmit`.
First enqueue is immediately before queue publication; first/last post are
immediately after `ibv_post_send` returns for accepted data WRs. The trace also
reports enqueue-to-post, post window, last-post-to-complete and first-post/API.
It excludes Python binding entry/return and batch allocation/free. For appended
submits each interval ends at observation of the entire batch, so use one submit
per batch (as tebench does) for the comparison below. Background progress does
not emit a caller-completion event. TCP or other transports leave RDMA post

## Known risks and verification limits

- Both prerequisite PRs were open when imported. The branch contains their
  implementations as explicitly attributed dependency commits; the new work
  should be reviewed against `tent-rfc5169-deps`. Rebase onto their final upstream
  versions before merging if they change. Upstream #5277's existing pipeline is
  reused rather than reimplemented.
- RDMA hardware throughput, the small-batch no-regression check, CUDA/GPU paths,
  and the Python binding's full API interval are unverified here. Fake verbs
  validate completion and posting mechanics, not NIC bandwidth.
- Smaller chunks can increase queue operations and signaled chain tails. The
  default keeps the existing QP-derived thresholds; tuning needs hardware data.
- Opt-in deadline arbitration retains its bulk ordering path. Its default is
  unchanged; the strict worker preparation budget applies to normal scheduling.
- MR reuse conservatively falls back on overlapping earlier registrations and
  zero-length requests. Cache lifetime is one pinned descriptor snapshot; no
  cross-call MR or route cache is introduced by this increment.
  A miss checks preceding registrations for overlap, so workloads without MR
  locality can pay an extra predecessor scan; that performance is unmeasured.
- Tracing adds clocks, atomics and stderr I/O when enabled. Its native C++ API
  interval and appended-submit semantics are defined above; do not present it
  as Python end-to-end latency or mix instrumented/uninstrumented bandwidth.
