# 同步对象存储副本

这里描述 RFC 第三部分：应用的 `Put` 同步写入对象存储，Master 将其作为
`OBJECT_STORAGE` 副本管理。它与[客户端持有的对象存储下沉](oss-backend.md)
是两条路径；对象存储读请求直接访问对象服务，不需要原写入客户端在线。
本次不实现异步写、后台迁移、跨命名空间搜索或独立对象目录。

## 成功意味着什么

启用 `ReplicateConfig.os_replica_num = 1` 后，可以同时请求内存等副本，也可以设置
`replica_num = 0` 仅写对象副本，无需挂载内存存储节点。
成功返回要求所请求副本的传输和一次对象 PUT 均成功，且对象副本与逻辑值的提交已经
进入当前 HA 任期的持久日志。对象服务本身的持久性由其服务契约保证。

```text
应用          写入客户端           Master / HA 日志             对象服务
 | Put             |                       |                        |
 |---------------->| PutStart              |                        |
 |                 |---------------------->| 分配所需副本、物理对象名 |
 |                 |                       | 持久化上传授权          |
 |                 |<----------------------|                        |
 |                 | 写内存副本（若请求）  |                        |
 |                 | PUT（最多一次）-------------------------------->|
 |                 |<---------------------------------------成功----|
 |                 | PutEnd（本次写入标识） |                        |
 |                 |---------------------->| 校验本次写入、业务准入  |
 |                 |                       | 持久化副本和逻辑值提交  |
 |                 |                       | 发布可读值              |
 |                 |<----------------------|                        |
 |<------成功------|                       |                        |
```

同步语义不能靠“上传成功后发一个通知”实现：通知丢失、Master 重启和替换旧值
都可能发生。完成通知只帮助回收；可读值由同一有序日志里的提交决定。

## 状态、引用与回收

上传记录属于 Master 的 HA 元数据，沿用 RFC 前两部分的日志与 v3 快照。
`StandbyMetadataStore` 既保存上传记录，也应用原有逻辑元数据变更；主节点维护
同一日志的镜像，用于判断对象是否仍被可恢复的值引用，不另建目录。

```text
持久授权 ──上传成功/完成通知──> 已上传 ──成功 PutEnd──> 逻辑值引用该对象
    |                            |                          |
    +──撤销、超时、失去引用──────+────────替换或删除────────+
                                 |
                                 v
                           退休记录（保留保护期）
                                 |
                         退休状态持久后 DELETE
                                 |
                 +---------------+----------------+
                 |                                |
           已确定上传结束                    上传是否结束未知
                 |                                |
           持久化移除记录                     保留记录，继续 DELETE
```

关键约束：

- 每次写入使用新的不可变物理对象名；逻辑键可以复用，物理名不复用。
- 完成和撤销校验副本编号及本次写入标识。对象写入以物理名为标识；对象转内存
  的替换使用新的 UUID。仅校验副本编号无法覆盖旧记录回收后的进程重启。
- 未持久授权不能 PUT；未持久提交不能发布；未持久退休不能 DELETE。
- 旧对象至少保留已有读租约的保护期；恢复后重新给予保护时间。
- 内存替换的提交和撤销独立于旧上传记录是否仍存在；GC 不会使一个有效尝试失效。
- 已退休对象不能重新成为可读值。重复完成通知和重复 DELETE 不会复活逻辑值。
- 清理在键锁内检查运行时和日志镜像的引用，等待持久化及对象 DELETE 均在锁外。

### 为什么“DELETE 成功”还不能立即忘记记录

HTTP 超时只说明客户端没收到成功，不能证明服务端已停止处理 PUT。可能出现：

```text
PUT 在服务端滞留 → 客户端超时 → Master 删除对象 → 原 PUT 才落地
```

因此，结果未知的上传记录需要保留，后续继续删除相同物理名。客户端只重试
完成通知，不重发 PUT；适配器必须配置为单次 PUT 尝试。明确未发起或已成功结束
的上传，才允许在保护期与删除完成后忘记记录。

**代价：** 写入客户端永久消失时，未知记录可能长期占用名额，并产生重复 DELETE。
`object_storage_max_records` 限制这些义务的总量，达到上限时拒绝新增对象写入，
保留现有已提交值。这里选择有界资源和删除安全，牺牲无限期故障下的写入可用性；
不会通过超时猜测服务端已终止，也不会靠扫描整个 bucket 推断归属。

## 实现取舍

| 选择 | 原因 | 成本或限制 |
| --- | --- | --- |
| 沿用 HA 有序日志及快照 | 授权、提交、引用与清理义务一起恢复 | 需要 HA、任期隔离与 OpLog；新增写入有授权和提交两个持久化边界 |
| 替换时分配新内存及新对象名 | 避免晚到写入覆盖新值；授权失败保留旧值 | 替换期间占用额外内存与对象空间 |
| 对象转内存也携带写入标识 | 防止旧完成/撤销误作用于新值，原子记录旧对象退休 | 这类替换仍需要日志持久化后发布 |
| 复用现有客户端控制线程及 Master 清理线程 | 不增加独立线程池和任务系统 | 对象服务 DELETE 慢会占用已有清理线程；每轮数量可配置 |
| 带写入标识的跨层替换要求所有副本成功 | 避免内存/NoF 部分成功被误发布为全部完成 | 此类替换不使用普通内存+NoF 的单侧成功语义；普通双副本写入保持原语义 |
| 活跃记录、退休记录分别建索引 | 普通写入不复制该键全部退休历史，退休清理不被活跃对象挤满 | 索引随记录生命周期维护，占用额外内存 |
| 批量接口逐对象执行对象 I/O | 复用有界单对象读写路径，保持每键失败和回收状态清晰 | 单个批次的对象 I/O 串行；吞吐依赖调用方并发，暂未复用适配器的批量并发调度 |
| 完成通知与 PutEnd 合并 | 成功路径减少一次 RPC 与日志屏障 | 客户端暂存失败时需要补报的通知 |
| 导入业务准入在提交日志前完成 | 导入被中止后不能产生“日志已提交、发布被拒绝”的悬挂状态 | 准入凭据保留到发布结束；已准入写入可能先完成，再由导入回收删除 |

## 配置及兼容性

Master 示例（HA、etcd、OpLog 参数需同时按集群配置提供）：

```text
--enable_object_storage=true
--object_storage_provider=s3
--object_storage_endpoint=http://127.0.0.1:9000
--object_storage_bucket=mooncake
--object_storage_region=us-east-1
--object_storage_prefix=my-cluster
--object_storage_path_style=true
```

Master 和客户端从各自环境读取凭据；配置 RPC 不传凭据。Master 需要删除权限，
客户端需要对应的读写权限。每个集群使用独立 bucket/prefix；外部写入或删除本
命名空间内的对象不属于本协议支持的并发修改。

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `enable_object_storage` | `false` | 启用同步对象副本 |
| `object_storage_max_object_bytes` | 256 MiB | 单对象上限 |
| `object_storage_max_staging_bytes` | 1 GiB | 每客户端对象暂存预算 |
| `object_storage_max_records` | 10000 | 包括待清理义务在内的记录上限 |
| `object_storage_maintenance_batch_size` | 32 | 每轮活跃扫描及退休清理各自的上限 |
| `object_storage_cleanup_interval_ms` | 10000 | 清理轮次间隔 |

配置启用时要求 fenced HA 有序日志，并禁用 DFS 和旧共享文件副本；不支持修改
已有记录的目标 bucket/prefix。对象写入目前仅支持 `os_replica_num=1`、同步写，
写入会话不支持请求对象副本；同键仍携带对象写入标识时，也会拒绝启动并精确撤销分配，可改用普通写入或在回收后重试。普通、批量、缓冲区和读会话范围读取均可使用对象副本。

**升级限制：** 新版本读取旧日志及 v1/v2 快照时转换旧的五种副本描述格式。
这不代表双向兼容；新增副本描述及写入标识改变 RPC/日志编码。不能混用新旧
Master 或客户端；需协调升级整个集群，且写入新格式后不能直接降级旧二进制。

## 阅读源码与验证

建议按以下顺序阅读：

1. `MasterService::AuthorizeObjectStorage`：持久授权和物理身份。
2. `Client::WriteObjectStorageReplica`：单次实际 PUT，失败结果与补报通知。
3. `MasterService::CommitObjectStorage`：校验尝试、业务准入、提交和发布。
4. `MasterService::CommitObjectAware`：同一日志里的旧引用退休与镜像。
5. `MasterService::MaintainObjectStorage`：保护期、持久边界和重复删除。
6. `MasterService::RestoreObjectStorage`：恢复校验、引用镜像及租约保护。

手工端到端驱动为 `mooncake-store/tests/object_storage_e2e.py`，使用真实 Master、
Python SDK、etcd 和 S3 兼容服务。`basic`、`budget`、`faults`、`stale`、`snapshot`、
`import`、`gc` 分别覆盖普通调用、容量边界、提交前后崩溃、旧请求重放、快照及日志回收恢复、
导入中止，以及 Start/End 或撤销之间旧记录恰好被回收。`object-only` 在无内存存储节点时复用
`basic` 的完整流程，覆盖纯对象读写、替换、批量失败、读租约、HA 恢复与迟到上传回收。
`performance` 对比相同有界对象 I/O 组件和完整 Store 路径，并比较对象功能
启用/关闭时的内存操作。输出目录保留日志、请求记录、CSV 和 SDK 指标；测试通过状态
以实际运行结果为准。

性能场景使用 8 个 RPC 线程、64 个处理线程及 30 秒 HA 租约，以容纳 32 个并发调用。
各对照使用相同配置；故障场景保留更短的租约。性能测量关闭校验和及故障注入目录，
在计时外比较读取内容。对象 I/O 指标包含客户端 HTTP、签名及缓冲处理，并非纯服务端
耗时；完整路径与该指标之差还包含内存传输和两次持久化 RPC，不能全部算作本地 CPU
开销。

```bash
python3 mooncake-store/tests/object_storage_e2e.py \
  --scenario basic --build /path/to/build --etcd /path/to/etcd \
  --endpoint http://127.0.0.1:9000 --bucket mooncake --output /tmp/object-e2e
```

构建故障测试需要 `-DMOONCAKE_ENABLE_TEST_FAILPOINTS=ON`，其余构建选项遵循当前
环境的 Store 测试配置。`stale`、`import` 和 `gc` 还需要构建 `object_storage_protocol_client`。

评审时应能解释：为什么旧租约保护期结束后，仍有记录不能忘记；为什么对象转内存
也需要持久提交；为什么收到上传成功通知不等于逻辑值已经可读。
